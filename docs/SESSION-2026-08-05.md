# Session log — 2026-08-05

What was built, what was found, and what was got wrong. `c72ddfe` → `308cc01` on `main`, 23 commits.
Tests **112 → 362**. Tools **15 → 26**.

The goal was seven capabilities: chart analysis, Pine Script development, workflow automation,
bandarmology, drawing, alerts, and UI automation — all showing the same data Stockbit shows. Six are
done and verified against live data. The seventh is blocked at Stockbit's end, evidenced below.

---

## What shipped

### Chart analysis
`technicals` (numbers) and `price_chart` (SVG candles, volume, SMA/EMA/Bollinger overlays, RSI/MACD
sub-panels, pivot support/resistance, caller-supplied annotations).

Three things the renderer gets right that a naive one does not: a warm-up gap **breaks** the overlay
path instead of sloping in from the origin and inventing a trend; annotations and overlays widen the
price scale *before* it is fixed, so a level outside the bar range is not drawn off-canvas; and
labels are escaped, because they are caller-supplied and land in markup a browser executes.

### Pine Script
`pine_script` emits Pine v6 — indicators, alert conditions, or a backtestable strategy, one script
per pane.

The design problem was not templating, it was **agreement**. A Pine script is a third place these
numbers appear and the easiest place to diverge — a sample SD instead of a population one, a
differently-seeded EMA. So each indicator is emitted as the builtin whose definition matches ours,
and support/resistance are embedded as **constants from Stockbit's bars** rather than recomputed in
Pine, which would use TradingView's data.

### Alerts
Rule engine (`alert_create`/`list`/`delete`/`check`) plus `stockbit-alerts`, a standalone daemon —
an MCP server only lives while a client holds it open, so a rule firing at 14:20 needs another
process.

Three channels: an append-only JSONL log written **first and always**, a native desktop notification
on by default, and an https-only webhook that is **off** unless configured. Fires once per bar,
recorded *before* delivery is attempted so a delivery failure cannot re-fire it every minute.

### Workflow automation
`workflow_list`/`workflow_run` and five recipes: `deep_dive`, `morning_scan`, `bandar_watch`,
`alert_sweep`, `pine_handoff`.

A workflow is **data, not code** — no `eval`, a closed template vocabulary, steps may only name a
registered tool. Handlers are captured by intercepting registration rather than kept in a second
list, which would drift the first time a tool was renamed.

### UI automation
Resolved as `stockbit_web`: check whether Stockbit is open, and open it in **your own** browser.
ADR-0002 already argued that driving a GUI solves a problem this project does not have — Stockbit has
a clean JSON API. This is the useful part of the idea.

### Drawing
Renders annotations, flows levels into Pine, reads your saved layout (`chart_layout`) and your real
chart configuration (`chart_settings`). The account write is built with full apparatus; Stockbit
discards it (below).

## The idea worth reusing

`src/analysis/series.ts` defines each indicator **once**, carrying both its Pine expression and its
local compute function. The Pine emitter and the alert evaluator both expand through it.

Written twice, those drift — one gets a Wilder-smoothed RSI and the other a simple one, and then an
alert fires on a day the chart says it should not have, with no way to tell which is wrong. A test
asserts every definition has both halves, so adding an indicator without a local implementation fails
the build rather than silently making alerts unevaluatable for it.

## Bugs found by running it, not by reading it

**Support levels above the market price.** BBRI fell from ~4000 to 3020 over the window, and
labelling a level by whether its pivot was a high or a low reported "support 3860, support 3615,
support 3580" on a stock trading at 3020 — three levels above the market, described as the floor.
Price fell through them; broken support is overhead supply. `kind` is now decided against the latest
close. Verified across BBRI, TLKM and GOTO: zero mislabelled. Neither of the two existing levels
tests caught it.

**`tasklist /V` took 92 seconds.** The obvious way to see whether a browser is running resolves the
window title and owner of *every* process. It would have stalled every chart render. One
`Get-Process` filtered to windowed processes answers the same question in ~650ms.

**Browser detection matched the project's own GitHub tab.** Matching any window title containing
"stockbit" counted `INo-xious/stockbit-mcp - Opera` as "Stockbit is open", so the assistant would
have decided there was nothing to do and told the user to look at a chart that never opened.

**A Chartbit endpoint that answers 200 and returns nothing.** A single-request bar range was added
and then removed after live testing: `data.chartbit` came back empty for every parameterization. The
runtime cross-check built into it rejected the response and fell back to the proven paged walk, so a
wrong inference cost one request and never produced a single wrong bar.

**A prototype-chain leak in workflow templating.** `{{constructor}}` resolved to `Object`. Own
properties only now.

**A Pine injection that escaping "at the door" would have missed.** A script title containing a
newline **escaped the header comment** and emitted `strategy.close_all()` as a statement — while the
same title was correctly escaped in its string use. Escaping has to be per-context. The security
assertions were also too crude: substring checks flag properly-escaped text, since escaped text still
contains its own characters. They now ask whether the payload appears as *code*.

## The one that mattered: a 42-agent review before the first write

`chart_layout_save` mutates the account, so it went through an adversarial Workflow review — four
independent lenses (rollback state machine, ADR boundary, failure honesty, whether the tests test
anything), each finding then handed to a skeptic told to refute it. 38 findings raised, 29 survived.

**The critical one would have destroyed the user's chart data.** `getChartLayout` omits the layout
blob above 4,000 bytes — a display guard. The write path read through it, and
`current.raw ?? (current.hasLayout ? "" : "")` returns `""` on **both** branches. For any real chart
(an empty layout is already ~500 bytes; sixty drawn levels is ~7.5KB) the write path believed the
account held nothing. It would have written a **0-byte snapshot**, logged `bytesBefore: 0` into the
audit trail, failed verification unconditionally because it was comparing against an empty string,
and then "rolled back" by POSTing that empty string over the user's drawings — while reporting
*"Nothing was left changed."* The honest round-trip, the tool's primary documented use, would have
destroyed the layout it was copying.

336 green tests never saw it, because every fixture was ~495 bytes.

The rule that came out: **a truncating read and a byte-exact operation must not share an entry
point.** `getRawChartLayout` now exists for the write path — uncached, unbounded, byte-exact.

Four other guarantees were strengthened in the same pass, each because the reviewers showed the code
asserted more than it knew: the rollback is read back and **confirmed** rather than inferred from a
2xx; a write whose request errored is read back before being called a failure, since a timeout can
arrive after the server committed; a verification that could not *read* no longer triggers a blind
rollback, because restoring over an unobserved state can itself be the destructive act; and writes to
one symbol take a lock.

## What I got wrong

**I claimed chart saving was behind a Pro paywall. It is not.** I read `PAYWALL_FEATURE_CHARTBIT` and
`isPro` gating in the page bundle and concluded a subscription was required. A collaborator pushed back — broker distribution, gated behind exactly that balance, already works
for him. Stockbit answers the question directly:

```
GET /paywall/eligibility/check?features=PAYWALL_FEATURE_CHARTBIT&company=BBRI
→ {"feature":"PAYWALL_FEATURE_CHARTBIT","is_eligible":true}
```

The paywall UI proves the feature *can* be gated, not that this account is. This was the **second**
time this project reached for a gate as an explanation — the first was mapping every 403 to the
Rp10m balance requirement, which would have told a user to deposit money to fix a Cloudflare block.
Same lesson: **when the server will answer the question, ask it instead of reading the UI's
intentions.** The eligibility route is now declared so it is cheap to ask. The wrong reasoning is
kept in `chartbit-layout-format.md` as a marked correction rather than deleted.

**I called a stale local cache a verified push, once before and nearly again.** `git ls-remote
--heads origin` is the only check that queries the server.

## Chart persistence: the elimination

`POST /chartbit/{symbol}/layout` and `POST /chartbit/template` both return HTTP 200 and store
nothing. Each variable was ruled out separately:

| variable | how it was eliminated |
|---|---|
| payload encoding | raw JSON, plain string, base64-ZIP — all 200, none stored |
| body schema | any other field → **400 INVALID_PARAMETER**, so `{content}` is right |
| query parameters | `version`, `symbol`, `user_setting_type` — no change |
| key format | `BBRI`, `bbri`, `59` (company id) — all 200-with-empty |
| mechanism | per-symbol layout **and** named template — both discard |
| host | module `93053` defines `q7 = https://exodus.stockbit.com` — correct host |
| headers | their axios sends `Accept`, an optional `User-Agent`, and the bearer — nothing missing |
| entitlement | `is_eligible: true` |
| an API key | none exists; Stockbit has no developer program |

And the decisive one: **Stockbit's own page chunk has no save wiring at all** — no
`save_load_adapter`, `auto_save_delay`, `onAutoSaveNeeded`, or `saveLayout` call site. The API
function is defined in their client and never called. a collaborator drew a trendline in their UI and saved
it; it did not persist there either.

Along the way the format was fully recovered from their bundle, and `Fj` — the save encoder that
could have made this unimplementable — turned out to be a three-line string replace
(`["D4LkIE","7a6YCE"] → "_seriesId"`), not encryption. Chart *properties* **do** persist, in
`/user-setting/configurations?user_setting_type=1` as base64 of a ZIP containing `layout.json` —
~12KB on this account. A different store from the per-symbol layout, which is why an empty
`chart_layout` does not mean nothing is configured.

Full write-up: [chartbit-layout-format.md](chartbit-layout-format.md).
