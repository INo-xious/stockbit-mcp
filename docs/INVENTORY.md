# Inventory

Everything this repository ships, in one place: the MCP surface, the skills, the four command-line
programs, the tool profiles, the environment variables and the decisions on record.

This is an **index**, not a reference. [`TOOLS.md`](TOOLS.md) is generated by `npm run docs:tools`
and is the authority on what each tool does, what it takes and what evidence backs it — a test fails
if it goes stale. Nothing here restates a tool description, because a hand-written copy of a
generated file is a copy that drifts.

Counts below were read off the running server and the route table at `stockbit-mcp@1.2.2`, not typed
from memory. To re-derive them: `npm run smoke` prints the tool and prompt totals, and
`npm run docs:tools` rewrites `TOOLS.md` from the surface itself.

## Command-line programs (4)

Four binaries, all with `--help` per command. **Unknown flags are an error, never ignored.**

### `stockbit-mcp`
The server itself, over stdio. `npm start` runs the built one.

### `stockbit-auth`
Login, the three token stores, and the trading policy.

`login` · `import-har` · `doctor` · `bootstrap` · `status` · `logout` · `trading-login` ·
`trading-status` · `trading-enable` · `trading-disable` · `trading-forget` · `paper-reset` ·
`trading-logout`

Worth knowing:

- `status` is the first thing to run when anything looks wrong. It reports every session, the
  trading mode and the IDX clock, and it spends nothing — validity comes from what happened the last
  time each credential was used, recorded in `session-health.json`. `--verify` spends a refresh to
  prove the token, and **that rotates the token family and ends the website session**, which is why
  it is not the default.
- `trading-enable --paper` is the safe way in: a local ledger, no real money, no PIN. `--live`
  places real orders.
- `trading-login` asks for the 6-digit PIN **at the user's own terminal**. It is never stored and
  never reaches the server.

### `stockbit-alerts`
The alert daemon — the thing that fires while no client is open.

`watch` (the default) · `check` · `test`

Telegram is environment-only: `STOCKBIT_TELEGRAM_BOT_TOKEN` and `STOCKBIT_TELEGRAM_CHAT_ID`.

### `stockbit-live`
Live tape and order-book reading. JSON on stdout; progress and errors never pollute it.

`scan` (the default) · `signals` · `explain` · `brokers`

## Tool profiles

All 139 tool schemas cost far more context on every turn than a conversation needs, so the server
registers a subset. `STOCKBIT_TOOLS` selects it:

| Value | Registers |
|---|---|
| *unset* | the `core` profile — **40 tools, 6 prompts**. What almost every user gets. |
| `all` | everything — 139 tools, 8 prompts |
| `core,<family>` | core plus one family, e.g. `core,trading` for the brokerage account, `core,eipo` for e-IPO |

If a tool seems to be missing, this is why.

## The request table

Nothing reaches a Stockbit host except through `src/http/routes/`. It is a closed table of **153**
request shapes, enforced by `src/http/transport.ts`:

| Host | Routes | GET | POST | PUT | DELETE |
|---|---|---|---|---|---|
| `exodus` | 116 | 95 | 11 | 4 | 6 |
| `carina` | 26 | 18 | 8 | — | — |
| `sekuritas` | 11 | 8 | 3 | — | — |
| **total** | **153** | **121** | **22** | **4** | **6** |

Adding a **non-GET** route requires an ADR *before* the code lands.

## The three invariants

Each has a test. Do not break them.

1. **Nothing reaches a Stockbit host outside `src/http/routes/`.** — `test/transport.test.ts`
2. **`define.write` never adds to the handler map `workflow_run` reads.** A saved recipe is data, and
   data must not be able to place an order. — `test/tools.test.ts`
3. **No module under `src/tools/`, `src/trading/` or `src/eipo/` may import `saveSettings`.** A server
   that can widen its own permissions has no permissions. — `test/settings.test.ts`

## Two things worth knowing before you call anything

**Absent is not zero.** A field missing from a result means the value could not be read — never that
it is zero. `readFrom` names the wire key each value came from, `derived` marks a computed value, and
`unmappedKeys` names what was not recognised. On account data the unmapped *values* are dropped
deliberately, because an unmapped field on a brokerage response may be an account number.

**After a write, read `outcome`.** `ok` is the only clean success, and it means the change was made
*and* seen when the account was read back. `rejected`, `not-visible`, `write-failed` and
`outcome-unknown` are not successes and must never be resent blindly. Nothing here rolls back.
